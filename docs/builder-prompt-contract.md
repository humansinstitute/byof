# Builder guidance and ordinary conversation

Current Napplet delivery uses [explicit native agent publication and independent final prose](agent-publication-contract.md). Receipt-based instructions below describe legacy owned-run recovery only; they must not be used for new requests.

Site administrators manage agent names and builder guidance in **Site Admin → System prompts** through `/api/v1/site/builder-prompt`. The editor defaults to the primary workshop's existing site prompt (`builder_prompt` row 1). An explicit prompt-scope selector also exposes existing additional workshop guidance; it is independent of the Tower/storage workshop selector. Additional workshops already have `workshop_prompts` rows: moving the editor does not migrate or overwrite them. The UI identifies the actual scope, and workshop management no longer embeds this editor.

Site-admin authorization, exact origin and CSRF checks guard the new entry route. The existing `/api/v1/host/builder-prompt` API retains its selected-workshop owner/site-admin contract for compatibility. Both routes reuse the same revision-checked save, immutable request snapshots and refresh of configured project AGENTS.md files. Saves require current `expectedRevision`, accept 1–16,000 nonblank characters and increment revision atomically. A concurrent save returns 409; reload fetches the latest saved prompt.

The default in `src/builder-prompt.ts` describes single-purpose, single-page Napplets built with self-contained HTML/CSS/JavaScript, responsive desktop/mobile controls and preservation of working behaviour. It directs the agent to answer, clarify, plan or implement according to the operator's latest instruction. It supplies pinned Napplet/NAP registry, NIP-5D draft and NIP-5A references, describes the implemented host-mediated identity/signing/storage and approved read-only relay subset and makes no publication claims. These references are guidance, never runtime fetch dependencies.

The UI sends ordinary conversation with no action selector. Compatibility with older clients' explicit modes and saved requests remains; new UI messages omit mode and use `auto`. There is no keyword router or answer/build intent classifier. Jev screens only the existing injection and unauthorized extraction questions. Structured JSON results are the technical completion contract: answers (including plans and clarification) have no source; builds contain the full page. Signed completion still requires matching project, request, conversation, generation and native receipt. Answers preserve source/revision/allowance; validated successful builds promote and charge once.

New requests copy saved guidance revision/text into an immutable `request_builder_prompts` row in the request transaction. Participant-supplied guidance fields are ignored. The same snapshot enters the dispatch outbox and replacement context hash; edits affect subsequent new requests only. Retries reuse the original payload. Replacement generations use the request's original guidance, not current settings. Context preparation checks snapshot equality and hash. Existing requests/outboxes without a guidance snapshot retain legacy bundled guidance and modes; they are never silently upgraded. The UI identifies the current saved version for new messages and the version used for each saved request (or legacy guidance).

`executionContract` in pipeline preparation is separate from editable guidance. New capable-builder definitions permit native public-web retrieval, scoped project-file editing and useful code/build checks. The delivered page keeps active assets inline and may directly call external HTTPS and secure WSS services. Those services must support browser CORS for the Napplet's opaque/null origin; ordinary mixed-content rules apply. Intentional public galleries may load validated HTTPS raster images directly. Builders must keep untrusted note content text-safe, reject credential-bearing/local-network image URLs, set descriptive alt text and `referrerpolicy="no-referrer"`, and provide visible loading/error/fallback UI. External scripts, imports, stylesheets, frames, plugins/objects, form destinations and other remote executable content remain forbidden. The builder must preserve source data, retrieval dates, units and caveats, show honest loading/offline/error/partial states and return complete final JSON. Secrets, unrelated private projects and host administration remain outside its scope; no credential-bearing proxy is provided. Guidance cannot alter grants, identity, signing, moderation, sandbox or artifact validation. The server supplies routing and validates owner/project/conversation/working directory. A prompt save does not activate execution.

Install immutable versioned preparation/candidate bundles and definitions with `scripts/followup-install.ts` (v18 or later for capable builders), then register their exact managed installation grant through the supported CLI. Both the preparation input pick and hashed replacement context carry `builderPrompt`; deploying source without installing the matching pipeline is insufficient. Preserve old grants for owned-run evidence and recovery. Optional server-only `additionalScopes` permit explicitly approved identities with separately pinned pipelines; they do not confer project ownership or enable arbitrary participants. New projects derive owner-bound conversation IDs and directories; existing projects retain their literal conversation and source history.

## Visible agent progress follow-up

Today the builder polls authenticated app request/deletion state. App WebSocket `/api/v1/events` carries room state; `safeProgress` permits correlated server status names and deliberately drops native text. Autopilot `/api/sessions/:id/events` supports adapter-native subscriptions and heartbeat/refresh fallback. A heartbeat or message refresh is not agent-authored commentary, and these session events are not currently an app-granted safe commentary stream. The managed pipeline broker permits exact definition submission and owned-run/delivery reads, not arbitrary session streams.

A follow-up should add a supported, run/request/project/generation-bound stream of explicitly public agent commentary/status/summary events. Validate adapter channel provenance, authenticate the app and project owner, apply the same receipt mapping and retirement/ban fencing, and persist bounded sanitized events with cursor/deduplication. Relay only deliberately visible commentary, never raw reasoning, private chain-of-thought, tool logs, unrelated session messages or secrets. Do not synthesize activity from timers. Keep signed terminal webhook completion authoritative. A generic runtime capability and narrow app grant would need independent implementation/acceptance before any WApp relay; this change adds neither a cross-repository stream nor fictional thinking events.

## Observable execution and host follow-ups

Autopilot owns actual execution history and native sessions. Its active installation registry grants the installation owner access to app-owned runs and sessions in ordinary APIs/UI, including an owner filter for installed app sessions. The signer and native binding stay app-owned; no identity rewriting is needed. Installation deletion/archive or an ambiguous owner relationship denies inherited access. Human owners may inspect/edit their existing definitions and use ordinary run/session controls; other owners remain excluded.

Project inspection links derive from configured Autopilot origin, exact installed definition and stored run/native completion receipts. They are private execution links, not published-app references. The browser needs the installation owner's or delegated operator's ordinary Autopilot login.

An authenticated host may submit a new follow-up via `POST /api/v1/host/projects/:id/requests` with a fresh requestId, exact current expectedRevisionId, prompt and operatorReason. The same configured owner/project execution scope applies. Host identity and reason are recorded immutably in host_request_audit; owner membership/allowance, room pause, native fencing, snapshots, deduplication and signed delivery remain enforced. A host cannot reuse an original owner request as a retry through this operation. This creates a new attributed instruction and preserves the original answer/history. It does not sign as the project owner or publish the project.

Capable preparation seeds index.html atomically from the app-authoritative current revision and preserves supporting project files. Installed bundles are immutable: installing a new capable definition does not rewrite old completed runs or snapshots. Old grants remain available for evidence/recovery.

## Workshop agent name

Hosts configure the agent name alongside workshop guidance. Existing workshops default to Agent 21. The current name labels conversation replies and activity without exposing prompt revisions. New requests snapshot the name with guidance, so retries preserve their original identity; preparation includes that identity in native turn instructions and managed project guidance. Legacy snapshots remain valid without a name.

The [Napplet bridge contract](napplet-bridge-api.md) documents injected methods, consent, signing policy, data scope and direct browser network boundary. Startup migrates only exact obsolete paragraphs in editable site/workshop prompts, preserving all custom text and queued snapshots. Fixed execution contracts and the managed local template describe the same HTTPS/WSS allowance and active-asset restrictions.
